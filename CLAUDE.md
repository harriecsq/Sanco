# Sanco

Desktop app for Sanco Medical Supply, a Philippine wholesaler of medical equipment. It imports from suppliers in Taiwan and China and sells to retailers. The app covers the whole workflow: client inquiry → booking → delivery → collection, and supplier PO → TT payment → receiving into stock.

Every PC keeps a full SQLite replica and syncs peer-to-peer over Tailscale. There is no server and there are no paid services. Any number of users and PCs is allowed. Windows only for now.

## Commands
- `npm run app`: run the desktop app (`tauri dev`, Vite on port 5173). After adding a route folder, restart it: a running Vite won't client-navigate to new routes.
- `npm run build`: build the frontend, typecheck and lint (needs to pass).
- `npm run bindings`: regenerate `src/lib/bindings.ts`. Debug app starts also regenerate it. Commit the file.
- `cargo test -p sanco-core -p sanco-net`: core, sync and network tests. Keep tests in these crates, because Tauri test binaries crash on Windows (`STATUS_ENTRYPOINT_NOT_FOUND`, missing comctl32 manifest).
- Several instances on one PC: `target/debug/sanco.exe --data-dir .dev/b --port 7472 --host 127.0.0.1` (flags also `--name`; `.dev/` is gitignored) next to `npm run app`. Headless peer: `cargo run -p sanco-net --example node -- --data-dir .dev/x --port 7480 --host 127.0.0.1 --create NAME | --join CODE`.
  - Instances started with `--data-dir` skip the single-instance lock and autostart. `--minimized` starts hidden in the tray.
  - Testing updates: `--app-version 9.9.0` reports another version to peers, `--installer PATH` shares that file instead of `sanco-setup.exe` next to the exe.
  - Driving the UI from a script: start an instance with `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=9301` and its own `WEBVIEW2_USER_DATA_FOLDER`, then use the Chrome DevTools Protocol on that port (Node 24 has `WebSocket` built in).
- `cargo clippy --workspace`: needs to stay clean.
- `npx tauri build`: NSIS installer.

## Architecture rules
- **One write path.** All writes go through `sanco-core/src/repo.rs` (`db.write(actor, |tx| tx.insert/update/upsert/delete(...))`). It stamps the HLC and `_vv`, bumps `row_versions`, writes `audit_log` and fires the change listener (`ChangeEvent`, origin Local/Remote) so the shell can emit `db-changed` and poke peers.
- **No stored derived values.** Stock on hand, receivables, PO receiving status and landed cost are SQL views or computed values, never columns. Dashboard KPIs and data issues (negative stock, numbers used twice, overpaid DRs, duplicates, …) are computed on request too (`domain/dashboard.rs`), not written as to-dos.
- **Generated child rows** use deterministic IDs: `ids::derived_id(source_id, kind)` (UUIDv5). Client-item rates use `derived_id(client, item)`. Deletes always win the merge, so a derived-id row can never come back once deleted: clear it (e.g. null price) instead of deleting it.
- **No SQLite foreign keys or UNIQUE constraints** on replicated tables (only the `id` primary key), because rows can arrive out of order. Duplicates are flagged by invariant checks instead.
- **New replicated table:** add it to `db/registry.rs` and a new migration, with the standard meta columns first (`id, _hlc, _site, _vv, _deleted, created_at, created_by, updated_by`). `registry_matches_schema` in `tests/repo.rs` checks they agree. Columns are TEXT or INTEGER only.
- **Units:**
  - Money is `i64` centavos (minor units for foreign currency).
  - FX rates are decimal text (`rust_decimal`).
  - Percentages (margins, VAT, % charges) are integer basis points in `*_bp` columns: 20% = 2000. Round half away from zero.
  - Quantities are integers in the base unit.
  - Timestamps are UTC milliseconds, displayed in Asia/Manila.
  - Calendar dates are `YYYY-MM-DD`.
- **Migrations are additive only.** Backfills are deterministic and do not bump the HLC or `row_versions`. Run `VACUUM INTO` before each migration. Views (`v_stock`, …) aren't replicated, so a later migration may drop and recreate them.
- **Database connections:** one writer thread with a job channel, plus read connections. WAL with `synchronous=FULL`.
- **Qwik static rules:**
  - Call `invoke`/`commands.*` only in the browser (`useVisibleTask$`, event handlers).
  - No `routeLoader$` or `server$`.
  - No dynamic `[id]` routes. Use `?id=`.
  - Inside `$()` and tasks: don't mutate module-level `let`s (wrap in a module-level function) or capture local functions (make them module-level). Put `q:slot` on each element, not on a `<>` fragment.
  - A child component prop computed inline from a signal (`title={MAP[sig.value].title}`) can be treated as constant and go stale. Pass a `useComputed$` signal's `.value` instead.
  - Route content is prerendered (in a hidden `q:template`) before anyone signs in. Load data with `useLiveLoad(tables, fn)` and read permissions inside `fn`, not at render. Visible tasks that load data use `{ strategy: "document-ready" }`.
- **Permissions (RBAC)** are checked in Rust on every command, not just hidden in the UI. Start each command with `commands::require(&state, Module::X, Action::Y)` (or `require_save`, `require_view_any`, `require_admin`); it re-reads the user and roles from the database. Sensitive values (`Field::Costs`, `Field::Margins`) are stripped in Rust when `!user.perms.sees(field)` (DTOs have `strip(&perms)`), and saves ignore margin inputs from users who can't see margins.
- **Seed rows** (default locations, charge types, roles) use `derived_id("<kind>", key)` and skip any existing row, even a deleted one. `domain::seed_defaults` runs at every node start. Roles are admin-editable: per module × action (view/create/edit/delete/approve), plus sensitive fields (costs, margins).

## Sync
- **Merge:** whole-row, keep the greatest `(deleted, hlc, site)`, so deletes win, then last writer. Each row carries a version vector `_vv` (site → last HLC it wrote). If neither side's `_vv` covers the other, the edits were concurrent: the losing version goes to `conflicts` (deterministic id and HLC taken from the lost version, so every PC records the same row) and is shown on the Dashboard.
- **HLC** = `millis * 1000 + counter`, below 2^53 so the frontend can read it as a number.
- **Delta pull:** rows by `row_versions.ver > watermark`. Accepted rows bump the local version, so changes relay through intermediate PCs.
- **Transport:** axum on `0.0.0.0:PORT`.
  - Only Tailscale ranges (`100.64.0.0/10`, `fd7a:115c:a1e0::/48`) and loopback are accepted.
  - Requests carry a bearer token derived by HKDF from the workspace sync key (local-only `workspace` table; a join snapshot carries it).
  - Peers get a `POST /poke` after local commits and after a pull that accepted rows (so changes relay). Every PC also pulls every 30 s.
  - Peers are the replicated `devices` rows (id = site id, host = Tailscale IPv4) plus addresses that poked us. Plain HTTP: WireGuard already encrypts.
  - Joining: a join code (Crockford base32 of key + inviter `host:port` + checksum) → `GET /snapshot` → open as a copy (never `new_identity`) → `Db::finish_join`.
  - **Updates** (`sanco-net/src/update.rs`): the installer copies itself next to the app; every PC serves it (`GET /update`, `/update/installer`). A peer's `app_version` is recorded from `/hello` even when the handshake then refuses it. A newer version shows a banner; "Update now" downloads it (size + SHA-256 checked), runs it with `/P /R` and quits. Bump the version in `Cargo.toml` (workspace) **and** `tauri.conf.json`.
- **Handshake** (`GET /hello`, `Db::check_peer`) rejects: schema mismatch, clock skew over 2 minutes either way, a known site with a different epoch, or a known site whose head version is below our watermark (restored or copied database). A database opened on a different machine or path takes a new site id automatically; the restore flow must open with `new_identity`.
- **Document numbers** are shared, like `DR-2026-0001`, with the format editable per type (`sync/numbering.rs`). A number is claimed with reachable peers before use (`Node::reserve_number` over HTTP, i.e. `numbering::reserve`, then `numbering::assign` inside the document's write). **Validate read-only before reserving** (e.g. `inventory::validate`): a write that fails after the reservation leaves the claim held, so the next document skips a number. Posted stock documents are never edited; they are voided and entered again. Numbers live only in `doc_numbers`; documents join it on `ref_id` and never store their own `no` column. On a clash after an offline period, the earliest `(assigned_at, id)` keeps the number, and only the PC that assigned the later one renumbers it (`resolve_clashes`, run after each pull).
  - **Typed numbers:** DR numbers are typed from the BIR booklet unless Settings sets `number_mode.DR = auto`. They are claimed exactly (`numbering::reserve_exact`, `doc_numbers.manual = 1`) and are **never renumbered**: an offline clash gets to-dos for both users and a "used twice" badge until someone corrects one (`assign_or_change`).

## Business rules
- **Margin is margin on price:** `price = cost ÷ (1 − margin%)`. ₱100 at 20% → ₱125.
- **Price resolution for a client and item:**
  1. The manual client-item rate.
  2. Otherwise landed cost at the client's margin tier.
  3. Otherwise landed cost at the item's default margin.

  The UI shows which rule applied.
- **VAT:** a checkbox on bookings, DRs and rates. The rate is in Settings (default 12%). `gross = net × (1 + VAT)`. Show net, VAT and gross.
- **Landed cost** = supplier price × FX + the cost-sheet charge lines. Charge types are an editable list (Freight, Customs duty, Brokerage, Bank fees, Import VAT, …), each per-unit, percentage of base, or per-shipment (a PHP total ÷ the cost sheet's `shipment_qty`; a sheet with a per-shipment charge but no qty has no landed cost). The PO "copy to cost sheets" button sets `shipment_qty` to the item's ordered qty.
- **DR number = BIR booklet number.** There is no separate manual reference. It may be typed at approval and is required to mark the DR delivered.
- **Sales flow:** BD request (open → quoted → won/lost; won only by converting into a booking) → booking (draft → confirmed → closed/cancelled) → DR (requested → approved → delivered, or cancelled; a delivered DR is voided, which returns its stock). DR lines name their lot.
- **Don't add edit locks** (user decision, 2026-10-22): BD requests (also won), bookings (any status but cancelled) and DRs (header and lines, also after delivery) stay editable. Keep only integrity checks: stock can't go below zero (an edited delivered DR moves the difference), DR qty can't exceed what's left on the booking, a booking line on a DR can't be removed. Posted stock documents (M6) are still void-and-re-enter.
- **Checks** are only checks received from clients (PDC if the check date is in the future). Supplier payments are TT entries on the PO.
- **Bank accounts** are the company's own accounts (Accounting → Bank accounts). Check deposits, bank transfers received and TT payments pick one (`bank_account_id`); the check's own "bank" is the client's bank and stays free text. No running balance is kept, only what the app moved. Used accounts are made inactive, not deleted.
- **Payments** (cash, check, bank transfer) get automatic `PAY` numbers plus an optional OR/CR no. A check is a payment with check fields; it counts as paid from receipt until it bounces or is replaced (a posted payment with `replaces_id`; "replaced" is never stored). Allocations go only to the client's delivered DRs (derived ids, cleared not deleted); the unapplied rest is credit. A DR with payments applied can't be voided or edited below what's paid.
- **Receivables** = delivered DR gross − counting allocations (`v_receivables`). Aging counts days past due = delivery + client terms.
- **Purchase orders** (draft → ordered → shipped → arrived → closed, or cancelled) stay editable except when cancelled; a received line can't be removed or go below what was received. Goods come in through receiving reports (`RR`, one location, expiry per line), which are void-and-re-enter like stock documents; received quantities are computed (`v_po_received`). PO prices, totals, FX and TT payments are cost data (`Field::Costs`). Receiving or placing a PO never changes cost sheets. Prices reach them only on request: a PO button copies all its prices and FX, and the item's cost sheet has "Update to supplier price" (`purchasing::apply_latest_price`, latest non-draft, non-cancelled PO), which also flags a pending new price.

## Glossary
- **BD:** Business Development. Client and prospect requests and inquiries (open → quoted → won/lost).
- **Booking:** a confirmed client order.
- **DR:** Delivery Receipt. Delivering one takes stock out and creates a receivable.
- **PDC:** post-dated check.
- **TT:** telegraphic transfer (supplier payment).
- **Landed cost:** the item's cost in PHP after FX and import charges.
- **Margin tier:** a client's default margin %.

- `sanco-core` holds the logic, so unit-test it there: price resolution, landed cost, VAT, `v_stock`, `v_receivables`, aging.
